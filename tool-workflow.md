# Tool Workflow — Cursor

## Primary AI tool used

Cursor (Agent) in this workspace, with repository files as the source of truth.

## How I provide project context

- `.cursorrules` encodes medallion constraints, quality-check names, Gold outputs, and “no secrets / no fabricated prompt history”.
- `tool-specific/cursor-workflow/spec.md` is the design spec I point Cursor at before generating layer code.
- `requirements-analysis.md`, `design-notes.md`, `data-model.md`, and `data-quality-strategy.md` are the persistent domain context.
- Each coding prompt names the target file path, the layer contract (Bronze raw / Silver flag / Gold valid completed orders), and the defect counts.

## How I use AI for requirement analysis

I paste or attach the evaluation brief and ask for contradictions, acceptance criteria, and Community Edition constraints — not for code. I then write `requirements-analysis.md` in my own words and only keep AI wording that matches the brief.

## How I use AI for pipeline design

I ask for Bronze/Silver/Gold table grain, flag-vs-delete behavior, and Gold inclusion rules. I reject suggestions that drop bad rows, that use Unity Catalog APIs unavailable on Community Edition, or that treat null FKs as referential-integrity failures (that would double-count completeness issues).

## How I use AI for code generation

I request one layer or one module at a time, with explicit schemas and function names that match the required repository structure. I do not ask for a single giant notebook. Python/PySpark is used for ingest and orchestration; SQL files own Gold measures so they can be reviewed independently.

## How I validate AI-generated code and logic

- Trace joins and window functions against `data-model.md`.
- Recalculate expected defect counts from `DATA_GENERATION_NOTES.md`.
- Run `pytest` on CSV generation and defect tallies locally.
- On Databricks, run row-count and quality-metric queries after each layer.
- Reject code I cannot explain (especially uniqueness windows and segmentation CASE order).

## How I use AI for testing and validation

I ask Cursor to propose assertions that match injected defects, then I tighten expected numbers myself (duplicate extras flag both the original and the copy). I do not accept tests that only check “row count > 0”.

## How I use AI for debugging

I paste the error class, the SQL/Python snippet, and the last successful layer counts. I ask for likely root causes (schema mismatch, null-safe join, overwrite vs append) and verify with a count query before applying a patch.

## How I use AI for data quality checks

I specify the five checks, reason codes, and “flag don’t delete”. I ask for metric SQL separately from row-level flags so the report cannot accidentally filter quarantined rows out of the denominator.

## What I avoid sharing with AI tools

- Real customer PII, production table dumps, credentials, tokens, workspace URLs with embedded secrets, and internal hostnames that are not in the public brief.
- Only synthetic CSVs generated by this repo are used.

## How I would reuse this workflow in production

1. Write a short spec (grain, SCD/overwrite policy, DQ thresholds) before prompting.
2. Keep layer contracts in repo rules so the agent cannot “helpfully” clean Bronze.
3. Generate code in vertical slices; run tests after each slice.
4. Store prompt evaluations next to the code change.
5. Treat AI output as a draft: code review, data tests, then merge.

## Lessons learned

- The brief’s file list is stricter than the prose (“4 checks” / “3 aggregations”). Implementing the file list avoided an incomplete submission.
- Specific prompts (“completeness on email, order.customer_id, order.product_id; null FKs skip RI”) beat “write data quality code”.
- Duplicate extras change uniqueness failure counts; tests must model that, or they fail even when the pipeline is correct.
